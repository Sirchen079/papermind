# 生成要求随文档回查

2026-09-27，源码进展，尚未进入 0.6.15 安装包。

研究者把成果带到新对话时，既需要正文和论文来源，也需要知道当时提出了什么任务。原流程只提供前两项，模型容易把草稿中的含糊表述当成用户条件。这次补齐可回查的原始要求，不生成新的任务摘要，不新增审批。

## 复用与实现

核对了现有 `Message.request_json`、文档版本父链接、回答保存来源，以及 [Pi 的会话上下文说明](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sessions.md)。Pi 的分支上下文组织可作参考；本项目已经有版本身份，不需要新增会话树或全局记忆系统。本次没有复制外部代码。OpenCode sessions 页面本轮未能读取，不作为实现依据。

`get_document` 和 `read_saved_document` 增加 `generation_request`：沿明确的人工版本父链接或回答保存来源，找到原始 AI 消息，再取同一对话内它之前最近的真实用户请求。保存通知不是用户研究请求。缺失、旧版无父编号或无效链接返回空值，正文照常可用。文档列表不展开这项信息，避免全库枚举时逐条追溯。

“已保存文档”和“关联成果”均提供可展开的“生成时的用户要求”，显示原话，并能返回原对话。AI 回读文档时同步得到该信息。它是历史背景，不能当成完整任务协议、当前用户决定或重新执行保存等操作的指令；后续修订和当前要求优先。没有额外模型调用、数据库迁移、硬编码 4K/FWI 规则或输出阻断。

## 验证及失败结果

- 35 项后端相关测试通过：真实请求回查、跨对话修订与回答保存继承、排除后来的请求和保存通知、无来源兼容，以及原有文档功能。前端生产构建通过；现有大包体提示仍在。
- 浏览器实际验证附件预览和文档详情可展开同一原始请求，返回任务原对话时关闭抽屉并加载正确对话。截图和记录在 `F:/论文管理/research-request-handoff-20260927`。
- 使用先前保存的 `research-routing-4k.md`（消息 45），在隔离副本的新对话中提交与上一轮完全相同的交接请求。真实 GLM-5.3 共 5 次调用，64,322 tokens，50.56 秒，0 次向量调用；原有两份导出文件哈希不变。
- 原始用户消息 44 明确为“每次请求最多给 4K tokens 的证据材料”。它完整出现在第 2–5 次模型输入中，未被截断。然而回答仍列出“4K 按整请求还是仅证据计”为待定事项。**条件沿用效果未通过，不能宣称这项改动解决了模型遗忘或提高了科研质量。**

上一轮交接是 5 次调用、64,320 tokens、35.19 秒；本轮没有成本或时间优势。两次单样本也不足以估计总体表现。还保留 IRCoT 总上下文与证据预算混淆等科学内容问题；本文不将模型回答当作已审核研究结论。

## 产品判断

已完成的是让研究者和 AI 都能回查真实任务要求，减少寻找原始对话的步骤。尚未证明模型会正确使用它，更未证明总核查时间下降。下一步应评估完整任务中的条件保留、错误修正和人工工作量，先检索成熟的任务状态与用户纠正机制，再决定是否需要显式任务记录；不围绕这一个数字继续叠提示词，也不以强制逐阶段确认弥补模型问题。

已知范围：只回查最近一轮生成要求，不总结此前所有决定，也不自动带入该轮的全部附件；人工稿显示的是其原始 AI 稿件的历史要求，不能覆盖人工修订。无来源的旧稿仍按原流程阅读和使用。

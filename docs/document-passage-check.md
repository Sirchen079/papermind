# 选段核查与文档来源优先

2026-09-26，未发布源码。接续 0.6.10 的文档复用流程，减少研究者把问题段落、文档版本和出处手动拼进新问题的工作。本轮不把模型核查视为自动事实认证，也不默认开启额外审查模型。

## 使用方式

在对话的“已保存文档”中打开研究稿或人工修订稿，选中正文的一段，点击“核查选中内容”。选文与具体文档版本会加入当前对话。已有问题保留；空输入框提供可修改的局部核查问题。用户按普通对话方式发送，不自动发送、不自动覆盖文档。

Agent 可以读取该版本及保存的论文、网页原文，必要时继续检索。任务以局部替换建议为主要产物，并简要说明改动和实际出处；不要求重写整篇。选文作为待核查研究稿，不作为原始文献证据。关联材料可以预览、移除，刷新或发送失败后继续保留。

## 发现的两个问题及处理

第一，模型分析与建议改写可能互相矛盾。最初实测中，它指出原稿把示例参数当成固定上限、速度比较缺少数据，但建议替换段落又恢复了类似断言。将任务组织成“局部修订为主、简短依据说明为辅”，避免同时生成多份长分析和改写；这没有增加输出拦截或复核调用。单次对照改善不能证明该问题已经普遍解决。

第二，自动整库检索只看问题正文。“核查选中的这段”没有研究主题，却触发向量与大模型重排，注入指令微调、改写评价等无关论文。现在从文档目录关联的材料带有结构化 `saved_document` 引用；聊天准备阶段把这类请求交给 agent 先读取明确的文档来源，不再用泛化操作指令自动预检索整库。Agent 的全文、关键词、向量及重排工具仍然可用，可根据材料和用户问题继续检索。普通问答、上传文件和旧版无结构化引用的材料保持原有行为。不是用“关联文档”几个字的匹配来决定路由，也没有新增数据库表。

## 三次真实调用

使用用户已配置的智谱 Responses、GLM-5.3、low，在千篇库隔离副本中核查此前真实生成的 CompAct 笔记。选中关于迭代次数、文档分段和推理速度的一段。界面测试捕获实际发送请求，再在相同材料上启用指定模型运行；核查标准预先保存，不送入模型。依据为已保存的作者 [GitHub README](https://github.com/dmis-lab/CompAct) 快照；本轮开发另行查看作者当前页面，两者不能混算为 agent 的阅读动作。

| 条件 | 用时 | 记账 tokens | 实际调用 |
|---|---:|---:|---|
| 初始核查问题 | 26.72 秒 | 23688 | 文本对话 3 次、BGE-M3 向量 1 次、大模型重排 1 次 |
| 改为局部替换建议 | 21.55 秒 | 27967 | 文本对话 3 次、BGE-M3 向量 1 次、大模型重排 1 次 |
| 文档来源优先 | 18.27 秒 | 19293 | 文本对话 3 次，无向量或重排调用 |

三轮均实际回读文档正文和保存的网页依据，全部原文档哈希保持不变。最后一轮不再注入无关初始论文来源，建议段落将速度比较改为待验证问题，并将具体参数置于 README 示例上下文。最终补充的引用序列化仅使结构化入口独立进入模型材料，另由回归覆盖；上述调用记录保留当时请求原样。

仍未达到全面质量验收：最后回答称“README/论文资源中没有这类数据”“仓库未报告速度数据”，但 agent 只读了保存的 README 快照，未全面核查论文及仓库。应限定为已读材料未提供对应数据。模型纠错后仍可能在其他位置扩大结论，不能把一次局部改善写成整份笔记正确。这三次是开发对照，存在模型波动；用时不是人工节省工时，不作一般速度或费用收益保证。

# PaperMind 的竞争重点与实现证据

2026-09-30，0.6.25 接通全页 OCR → 本机 Markdown → AI 阅读与检索索引，减少研究者下载后另找识别工具、复制正文、手动建立检索库和追踪后台状态的步骤。上传、公开 PDF 获取与调研导入共用现有转换与缓存机制；未配置先等待、重启可继续、旧库不自动重识别。[实测](releases/release-0.6.25-validation.md)完成两篇 30 页和一次界面补验，冻结程序保留 1006 篇旧资料。模型仍会错读表头和数字，因此继续保留原页回查；没有用这些工程结果宣称已经测得科研提效或竞品优势。以下保留此前阶段记录。

产品状态更新：2026-09-27；竞品资料核对：2026-09-26。竞品部分依据官方公开说明，未做同材料、同问题的账户内盲测；功能存在不等于效果相同。本文把已实现的能力、定位判断和待完成的验证分开。

## 竞品已经做到的事

源码另补上成果的原始生成要求回查，复用消息与版本关系，让研究者在文档和附件预览中直接核对条件。真实 GLM 仍重复询问已明确的预算口径，故只确认流程可追溯，不声称模型质量改善；详见 [生成要求与跨对话交接实测](document-generation-context.md)。

持续研究检查另发现摘要前截断会丢失较晚纠正，且超长摘要会被整份丢弃。源码复用 Pi 的结构化接续思路修复输入选择、工具操作序列化和部分摘要保留；真实 FWI 压力重放保留了近期核对稿与摘要，但模型解释仍不可靠，不记作科研质量通过。详见 [长研究对话接续](research-context-compaction.md)。

随后补齐同一个问题下连续阅读原文时的工具批次压缩，真实三篇任务经过 5 次摘要后成功保存，新旧文件与来源关系验证通过；同时发现关键论文事实经过多次摘要后丢失，导致方法可用性判断错误。下一步优先复用逐篇材料与科研精读技能，降低综合阶段对单份会话摘要的依赖，详见 [多篇阅读接续实测](active-reading-compaction.md)。

| 产品 | 官方资料明确支持的能力 | 对我们的要求 |
|---|---|---|
| Zotero | 默认本地保存数据；PDF 标注可加入笔记，并携带引用和返回原 PDF 页的链接。[本地与同步](https://www.zotero.org/support/sync)、[阅读与笔记](https://www.zotero.org/support/pdf_reader) | 本地存储、笔记和原文回查是基本功，不能单独称为领先优势。不能只依赖“有 AI”来替代资料管理的可靠性。 |

## 我们选择的使用场景

研究者把已有论文放进本地项目，持续加入新论文、阅读和修改，形成可以反复回查和更新的研究成果。AI 可以连接用户选择的网络模型，也可以使用已支持的本地运行时；用户不需要自行部署服务器。“本地”指项目和工作流程落在桌面，不表示网络 API 调用不收费或全文永不离开机器。

差异化假设是上述能力的组合：**长期本地项目 + 自选模型 + 大库检索 + 可回查的研究成果 + 持续协作的 agent**。核心是帮助研究者高效科研，减少找、读、整理、比较和修改的工作量；自动综述是其中一种产物。用户不要求完全自动成稿，不能将此误设为产品成立的必要条件。这不是经竞品盲测证明的独有能力，更不能从“1000 篇可以存进去”推导出“1000 篇都被正确理解”。

## 使用架构：项目、问题、材料与成果

产品的主路径是：带着问题进入项目 → 选择材料范围 → agent 查找、阅读与比较 → 得到可回查的研究成果 → 研究者纠正或调整方向 → 继续沿用。第一份成果可以是一张方法比较表、一段解释或实验准备笔记；整篇综述按任务需要生成。

“All in one”首先意味着材料、判断和成果能贯通。阅读器、对话、综述、知识页和汇报导出共用项目上下文，减少重复上传、复制和解释。近期投入集中在文献研究主线；图谱、更多导出形式和技能数量的扩充排在主线之后。

下面是目标使用架构，并非所有入口已经如此实现：

| 研究者看到的入口 | 应承担的职责 | 复用现有能力与对象 |
|---|---|---|
| 研究主页 | 开始一个问题，或找回正在进行的研究与成果 | 项目 workspace、最近工作目录、已有页面深链 |
| 论文库与阅读器 | 导入、筛选、读原文；把选文和论文直接带入研究 | Paper、全文与页码、标注、材料附件 |
| 持续研究 | 带着问题补查、比较、讨论、修改；可随时阅读阶段成果 | 现有 agent 对话、阅读工具、来源快照、文档编辑 |
| 批量专题综述 | 处理用户明确选定的一批论文，展示材料覆盖与章节进度 | LibraryReview、逐篇分析、检查点、分章草稿；通过已有 read_review 接入对话 |
| 成果与积累 | 查阅比较表、笔记、章节及其来源和版本，并继续使用 | 已保存文档、人工修订关系、知识页；先复用现有入口，再评估是否需要独立页面 |

用户描述问题、材料范围和希望得到的成果。任务方法由系统结合既有技能组织，并允许用户调整；日常使用不要求先认识 Nature 的目录结构、向量模型或不同内部任务类型。首次模型连接仍在设置页完成。

## 架构分工与现成方案

复用现有项目、材料、对话、后台任务和文档版本，在缺失的交接处补关系。先统一材料范围、成果引用与恢复行为，再考虑数据模型合并，避免一次重构牵动已有可用流程。

| 部分 | 负责的工作 | 设计边界 |
|---|---|---|
| 本地应用 | 原文、精确定位、数据保存、版本、进度、用量与恢复 | 用户无需部署服务器；可连接网络 API。模型不承担持久存储或精确计数。 |
| 检索层 | 书目、词法与向量召回，再按任务重排和获取原文 | 向量返回候选材料；研究结论来自后续阅读和比较。 |
| 大模型与科研技能 | 问题拆解、阅读、归纳、比较、写作和局部修订 | 能返回原文补读，阶段成果尽早可见；缺失处局部说明，继续完成已有依据的部分。 |
| 研究者 | 研究方向、关键取舍、专业纠正与最终采用 | 随时介入；普通检索、阅读和草稿生成自动推进，避免逐步审批。 |

现成方案检索仍是实现前的第一步。Agent 问题优先查 Pi、OpenCode、Claude Code、Codex 的公开实现或官方文档；科研方法优先查 Nature 和适用的成熟技能。对每个实际缺口记录“已有机制、如何复用、仍缺什么”；查阅文档不等于获得代码复制许可。

本次复核的适用机制：

- [Pi 会话](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sessions.md)提供自动保存、按工作目录恢复和分支接续。沿用其保留上下文与明确接续位置的思路，适配研究项目和成果引用；不直接迁移整个运行时。
- [OpenCode Skills](https://opencode.ai/docs/skills/)提供技能发现与按需加载。复用这类分层加载方式，结合已内置任务路由；它本身不保证具体模型会正确使用技能。
- 内置 [Nature Writing 工作流](../backend/builtin_skills/nature/nature-writing/static/core/workflow.md)已包含局部修改、术语一致性及只暂停依赖未决信息的部分。应用要把原稿、依据和修改关系交给这些方法使用，并保存结果；无需另建全局审批链。
- Zotero 的笔记回查、Elicit 的证据提取与综合说明“有引用”和“能生成报告”已是竞争基线，官方来源见上表。差异化要落实到一次研究中减少多少找材料、核查和返工。

后续每项改动先回答：服务哪个研究任务、接在哪一步、复用什么、减少哪种重复劳动、怎样验收。若局部优化不能解释它对整条流程的作用，先调整优先级。

## 一条任务如何验收整体

以“FWI 目标函数在噪声、振幅误差和实际数据条件下怎样选择”为连续任务，先交付有来源和适用条件的比较及实验准备笔记。研究者纠正其中一个关键判断后，沿修订稿追问；关闭再打开项目，找到既有成果；加入新材料后更新有关比较。用户可直接要求完整综述，这条验收也不要求先写完整综述才能推进。

记录研究者的检索阅读、操作、核查、纠错主动时间，另记模型等待、重复复制和遗失上下文的次数。质量评价关注关键研究决定是否有依据、条件是否对齐、成果是否可继续使用。先用可人工核对的任务发现断点，再按 [已有人工效率方案](research-assistance-evaluation.md)组织相近难度任务对照；Codex 审计不冒充真实用户工时，模型自评分不作为质量结论。研发验收要求不转化为产品中的输出拦截。

## 2026-09-26 千篇存储、索引与界面实测

在原始百篇库的独立副本中，加入来自同一官方语料的 900 篇真实论文。扩展库包含更多 LLM、问答等相邻主题，用于检验混合论文库规模，不作为千篇系统综述样本。首次下载有 4 篇连接失败，保留结果并重试后，1000 篇全部完成；索引分批执行并复用已完成片段。

最终只读审计核对了清单集合、1000 份不同 PDF 的内容哈希、数据库正文页码、当前分块算法生成的全部文本和顺序，以及每条向量的模型、维度、有限性与非零性。结果：1000 篇、16688 页、63788882 正文字符、72912 个 1024 维 BGE-M3 片段；无缺失、重复 PDF 或过期片段，SQLite quick_check 为 ok。原百篇 PDF 另复制入千篇库的 PDF 根目录，并核对哈希，避免依赖外部库路径。

另在私有数据库副本启动桌面程序使用的本机后端，以浏览器验证千篇任务：每页只渲染 20 条来源；可查找第 1000 篇并查看真实摘录及页码按钮；PDF 文件接口返回 PDF；导出材料清单含 1000 个不同论文编号。1440px 桌面与 390px 窄屏截图已检查，无页面异常或横向溢出。本机单次页面加载到千篇计数显示为 406ms，不代表普遍性能。此次只创建待生成任务，没有调用模型生成千篇综述，也没有通过点击页码按钮检验 PDF 翻页。

隔离界面测试最初因语料数据库由 create_all 建表、未记录迁移版本而启动失败；验证全部模型表字段后，仅给测试副本补记迁移版本。第二次因测试脚本使用不存在的 PDF 路径而失败，改为产品实际 `/api/papers/{pid}/file` 接口后通过。没有为测试修改产品迁移或文件访问行为。

开发机原始证据：`F:/论文管理/real-corpus-1000-20260925/corpus-audit.json`、同目录 `corpus-audit-rows.json`，以及 `F:/论文管理/thousand-library-ui-20260926-v3/result.json`、截图与 `coverage.jsonl`。这些结果证明千篇材料管理和索引完整性，不证明检索相关性或综述内容质量；相关数据和模型密钥不加入分发包。

## 语料与复现

依据 [ACL Anthology 官方元数据说明](https://aclanthology.org/faq/api/)，读取其官方 GitHub 仓库中的 2023、2024 年 ACL、EMNLP 和 Findings XML，以及对应公开 PDF。

选样条件为标题含 retrieval 或 RAG，标题或摘要含 generation、language model 或 question answering；在 311 篇候选中按论文标识的 SHA-256 排序选取 100 篇。保存 XML、内容哈希、标题、摘要、作者、官方地址与 PDF 哈希。它是覆盖多种应用的固定主题样本，不是系统综述的检索方案，也不代表领域全貌。

开发用脚本 `backend/scripts/validate_real_corpus.py` 提供四个独立阶段：

```powershell
python scripts/validate_real_corpus.py --data <独立测试目录> prepare
python scripts/validate_real_corpus.py --data <独立测试目录> index
python scripts/validate_real_corpus.py --data <独立测试目录> retrieve
python scripts/validate_real_corpus.py --data <独立测试目录> review
```

首次目录必须为空；模型配置只写入该测试数据库。`index`、`retrieve` 和 `review` 会调用所配置的真实模型 API。下载和已完成索引可复用；综述任务保留逐篇及章节检查点。测试数据库、密钥和下载 PDF 不加入源码或安装包。

## 已验证结果

- 100 篇不同论文、100 份不同 PDF 全部入库，正文约 6,242,396 字符，保留 1,588 个实际页码。
- BGE-M3 成功索引全部论文，共 7,092 个片段，逐篇索引耗时合计 227.85 秒。
- 8 个由官方摘要确定目标文献的中文问题，在前 12 个片段中均找回对应英文论文；6 个目标排在首位，另两个为第 2 和第 6。查询耗时中位 0.218 秒，首次查询 4.64 秒，其余约 0.20–0.23 秒。该耗时包含此环境下的查询向量请求，不代表其他网络或模型服务的延迟。
- 返回的正文检索片段都有页码；标题摘要片段不虚构页码。
- 原生 PDF 页码、参考文献解析、检索及阅读相关两组后端测试共 68 项通过；前端构建和 134 项测试通过。
- 浏览器验证综述来源直接打开 PDF 第 7 页，并覆盖上次阅读到第 2 页的恢复位置；无页面异常。390px 视口无页面横向溢出，仅作为布局检查。
- 百篇逐篇分析全部完成，无失败回退。随后主动暂停，确认原执行进程退出，再用新进程继续同一任务。100 篇分析的内容哈希全部不变，100 篇标记为复用，恢复到下一次综合请求前的文本模型调用数保持 103，未重复进行逐篇分析。该验证覆盖主动暂停后的进程重启续跑，没有模拟强制断电。

下载过程中有 5 个连接异常，复用已下载文件后重试完成。匿名 GitHub API 曾触发配额限制，改用官方原始 XML 并保存内容哈希，未更换语料来源。

这些检索结果属于指定文献召回抽查，没有穷尽标注所有相关论文，不能作为通用检索精度、事实正确率或综述写作质量的证明。

## 高思考等级的空输出诊断

在测试库副本中，以相同段落、原文和修改要求比较低/高思考等级。三段低等级均返回正文，高等级均空返回；原段落输出上限分别为 754、600、1296 token。测试未保存修改，也未改变原始测试库或用户项目设置。

继续以第一段的完全相同请求探测输出额度：754 和 4096 上限均收到 `incomplete / max_output_tokens`，其中推理分别占 749 和 4087 token，输出没有正文消息。8192 上限成功完成，实际输出 8000 token，其中推理 7594，耗时 165.08 秒。这证明该样本的失败来自总输出额度不足；并不证明所有空响应都是这一原因。

开发版将正文长度目标与推理预留分开。中/高/更高等级初始预留为 4096/8192/16384 token，受上下文容量约束，至少留出一半窗口供输入材料。仅在明确的额度耗尽且无正文时扩大额度重试一次，重新预算来源空间；不会丢弃非空正文，也不降低用户配置的思考等级。段落修改依旧只返回预览。

相关后端测试 65 项通过，覆盖 4K/8K/32K/1M 窗口、推理额度、来源保留、条件重试、非空部分正文保留、缓存复用、千篇流程和模型接口。8192 探测返回稿恢复了 BERGEN“候选解释、待验证”的限定，但仍有过强归纳；这是输出可用性修复，不能当作科学内容质量全面通过。

修复后再次通过真实 `editing.propose` 入口运行同一段落：发送消息的哈希与修复前完全一致，配置仍为高思考等级，实际输出上限 8946，153.91 秒返回修改稿，报告总用量 17652 token。测试确认原文及版本未保存改变；此次成稿恢复了“候选解释而非已验证机制”的区分，仍不据此推断其他段落或整篇质量。代码尚未打包进已交付的 0.6.3 安装程序。

## 检索片段与简报在写作链路中的保留

检查百篇库的六个章节，发现每章召回 12 个片段后，`chapter_sources` 再按方法、结果等固定类别选材，最终 12 个来源中没有一个直接采用召回片段。英文片段与中文标题的字面重合少，语义召回结果被类别加分覆盖。这里统计的是相同片段是否被直接采用，不代表旧来源与召回片段完全没有内容重叠。

修复后分配一部分位置给章节检索结果，另一部分保留论文背景，并优先覆盖不同论文。相同的六组召回结果每组保留 6 个片段。空索引、重复命中、来源页码及所选论文范围仍正常处理。没有增加核查批准或拒绝输出流程。

对最后一章做同模型、同前文和同论证简报的真实前后对照，仅改变原文选材；两次调用分别 28.33 和 28.27 秒，均返回正文，原稿没有保存改变。新稿仍将 BERGEN 的候选解释表述为确定归因，也仍有领域空白过度概括，因此该实验只证明检索材料进入了写作，不能证明内容质量稳定改善。

继续追查发现 BERGEN 的逐篇简报末段含“假设性解释”及“未做深入验证”，但旧分组综合按字符取开头，丢掉了末段的限定。分组、分层合并、全篇规划和章节简报现改为按段共享预算，保留开头之外的结果和局限。相关 48 项回归通过，包含二十篇长简报末段保留、千篇分层处理、整体上下文额度及检查点复用。

对包含 BERGEN 的 20 篇分组另做真实前后对照，两次分别耗时 40.44 和 45.16 秒。检查保存的输入确认：旧输入没有上述限定，新输入保留了两处原词。新综合没有再复述旧稿中将 oracle 结果泛化到 TruthfulQA 的说法，但也没有明确转述“假设性解释”，且仍有跨论文关系过度概括。因此本轮确认了材料传递缺陷的修复，未确认模型能稳定保留所有限定。诊断脚本最初用不匹配的同义句检测，误报新输入未保留限定；这里按实际输入原词核对，旧日志保留，未重新生成或手改模型正文。
